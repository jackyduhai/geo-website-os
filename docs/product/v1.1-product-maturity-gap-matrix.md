# GEO Website OS v1.1 — Product Maturity Gap Matrix

- **状态**：ACCEPTED AS v1.1 ROADMAP（蓝图存档，**非 v1.0 范围、非当前 Release Blocker**）
- **日期**：2026-09-27
- **基线关系**：v1.0 Architecture Frozen（`9f0f4c1`）→ 19A Release Readiness PASS（`05aac3f` / `17367c3`，P0=0、P1=0）
- **参照系**：成熟企业 CMS（炎酷 CMS）的完整日常运营闭环；**只抽象能力本质、映射到 GEO Native 架构，不做功能数量 1:1 复刻**
- **纪律**：新增能力先独立 Discovery → 架构影响评估（必要时 Architecture Change Review）→ Implementation → Gate；不得因成熟 CMS 有某功能就解除 v1.0 Architecture Freeze。

---

## 定位

本文不是"炎酷 CMS 功能复刻清单"，而是：以成熟企业 CMS 的运营能力为参照，判断 GEO Website OS v1.0 已完成什么、缺什么、哪些应该补、哪些应该重构后补、哪些应该保持不做。

## 一、核心结论

当前 GEO Website OS：

> v1.0 = GEO Native Core + CMS 基础能力 + 产品化 Admin 能力 + 安装 / 升级 / 健康 / 覆盖 + 架构冻结

已经形成：

```
Entity Graph → Content → Composition → SEO / GEO / Schema → Health → Coverage
```

因此 v1.1 的主要问题已经不是"还能不能做官网？"，而是"能不能让一个真实企业长期运营这个官网？"——这也是成熟 CMS 与当前 GEO Website OS 的主要差距。

炎酷 CMS 当前公开能力中，最值得借鉴的不是某一个 UI，而是其完整的日常运营闭环：内容发布、定时发布、回收站、素材、统计、留言、模板在线编辑、备份升级，以及 AI 内容生产。

## 四、P0-1 Content Lifecycle

**当前问题**：系统已有 draft / published / archived，但还没有形成成熟 CMS 意义上的生命周期运营闭环。成熟 CMS 已把"全部 / 已发布 / 草稿 / 回收站 / 定时"组织成实际日常工作流。

**v1.1 建议演进**：

```
Draft → Scheduled → Published → Expired → Archived → Trash → Restored / Purged
```

但不要简单照搬文章状态。必须兼容 **Entity / Content / Page / Block**，形成统一的 **Publication Lifecycle Contract**，而不是给 Content 单独造生命周期。

## 五、P0-2 Scheduled Publish

炎酷 CMS 支持设置未来发布时间，到点自动前台可见。GEO Website OS 应增加 `publish_at` / `unpublish_at`，但不要马上扩成复杂 Workflow Engine。v1.1 只解决定时发布 / 定时下线，并且 **PublicIndex / Sitemap / Schema / GEO / Search 必须全部跟着 Publication State 变化**。

这是 GEO Native 与传统 CMS 的重要区别："发布"不是只改变前台页面状态，而是改变整个机器可读知识集合。

## 六、P0-3 Trash / Recycle Bin

目前比较明显的成熟度缺口。炎酷 CMS 的文章删除不是立即物理删除，而是进入回收站、可恢复为草稿，彻底删除才清理图片。

GEO Website OS 建议：

```
Delete → Trash → Restore → Draft
Purge → 关联 Media 检查 → Relation 检查 → Search / Cache / GEO 清理
```

尤其不能出现"删除 Entity → Relation 残留 → GEOGraph 残留"。Trash 应与当前 EntityRelation / ContentEntity / Media / PublicIndex / PageCache 一起设计。

## 七、P0-4 Page Manager

当前 Page Composition / PageResolver / Section Composer / Template Registry 已具备技术基础，缺的是"页面资产管理"这个运营后台。

```
Pages
├── Home
├── About
├── Contact
├── Landing Pages
├── System Pages
└── Archived
```

每个 Page 显示：名称 / 类型 / 状态 / Locale / Template / SEO / GEO / 最后修改时间 / 发布状态，并支持编辑 / 复制 / 预览 / 发布 / 下线 / 归档。不是新增 Page 架构，只是给现有 Page / Composition 增加运营管理层。

## 八、P0-5 Media Library Lite

炎酷 CMS 已把图片集中管理、分类、日期归档，并支持编辑器直接调用。GEO Website OS 虽已有 Media，但需要真正成为网站素材资产中心：

```
Media Library
├── All
├── Images
├── Documents
├── AI Generated
├── Unused
└── Recently Added
```

核心字段：filename / type / size / dimensions / alt / caption / source / ai_generated / created_at / usage_count。重点加入 **Usage Graph**（如 logo.png → Header / Homepage / Product A / SEO OG），删除前能知道"这个素材正在被哪些实体、页面和内容使用？"——比传统 CMS 素材库更适合 GEO Website OS。

## 九、P0-6 Inquiry Center

当前已有 Inquiry / Form / FormField / FormSubmission / Attribution，不是缺数据基础，而是缺运营闭环。

```
Inquiry Center
────────────────
新询盘 / 待处理 / 处理中 / 已处理 / 垃圾
────────────────
来源 / Landing Page / UTM / Device / 时间
```

允许 Mark Spam / Assign / Mark Read / Add Note / Archive，但不要演变成 CRM Opportunity System，边界继续保持。

## 十、P0-7 Attribution

Inquiry Center 的关键补全。统一记录：source / medium / campaign / term / content / landing_page / referrer / device / locale。

完整链路：广告 → Landing Page → 表单 → Inquiry → Attribution。未来才能真正分析"哪个 GEO 页面 / 哪个内容 / 哪个入口带来了询盘"。这是传统 CMS 的能力基础，也是 GEO Website OS 更应强化的方向。

## 十一、P1 访问统计 Dashboard

炎酷 CMS 提供按日聚合（today/yesterday/this week/.../total）并统计 IP 数和浏览量。GEO Website OS 不照搬全部口径，升级成四个维度：

- **Traffic**：PV / UV / Sessions / Top Pages / Entry Pages
- **Content**：Top Content / Top Product / Top Case / Top Search
- **GEO**：AI-readable pages / Entity coverage / Public entity count / GEO graph growth
- **Conversion**：Inquiry / Form submission / CTA click / Landing Page

## 十二、P1 Template Center 增强

当前 Template System 已比炎酷 CMS 的简单模板选择更完整，不重做。v1.1 增加：Installed / Active / Industry / Preview / Compare / Compatibility / Version / Upgrade，尤其加强 Template Compatibility（Theme API / Component API / GEO Contract / SEO Contract 版本兼容）。

## 十三、P1 Visual Editing 与 Composer 融合

炎酷 CMS 做到"左侧模板/样式、右侧真实前台实时预览，预览不写数据库"。GEO Website OS 不退回传统模板选择器，而发展：

```
Page Manager → Section Composer → Real Preview → Device → Light/Dark → Locale
```

即安全结构化 Canvas，而不是自由 Canvas。

## 十四、P1 对象存储

炎酷 CMS V2.5 已支持 Local / COS / OSS / Qiniu 并提供已有素材迁移。建议 GEO Website OS：

```
Storage Adapter
├── Local
├── S3
├── OSS
├── COS
└── Custom S3 Compatible
```

不直接为每个平台建立独立业务逻辑，而是 Media → StorageContract → Driver 统一解决。属于架构可兼容增强，不推翻当前 Media。

## 十五、P1 AI Content Engine

双方产品方向真正分叉处。炎酷 CMS 提供 AI 初稿 / 续写 / 改写润色 / 摘要 / SEO 三件套 / 关键词提取 / 批量文章 / AI 生图，并将 AI 产物存为草稿供人工审核。

GEO Website OS 不只是复制"AI 写文章"，而是：

```
Entity + Facts + Evidence + Question + Audience + Intent
  → GEO Content Engine → Draft → Health Check → Coverage Check
  → Human Review → Publish
```

即 AI Content = GEO Knowledge Production，而不是 AI = Article Writer。

## 十六、P1 AI 批量生产

炎酷 CMS 可按关键词批量生成文章草稿、异步处理失败项。GEO Website OS 可做得更强：

```
关键词 → Entity Match → Scenario Match → Content Template → AI Draft
       → Evidence → Coverage → Health → Human Review
```

形成 Generate → Validate → Review → Publish，才真正与 GEO Website OS 架构吻合。

## 十七、P1 多语言内容工作流

当前前台 zh / en 主链已完成。v1.1 不重新造 Translation System，而是增强：Source → Translate → Review → Publish。状态：Not Translated / Draft Translation / Review / Published / Outdated。尤其源语言内容修改后自动标记译文 Outdated，多语言才进入真正运营阶段。

## 十八、P2 Admin i18n

当前 TD-164：Admin UI 仅中文。问题真实但不阻塞 v1.0。v1.1 做 Admin zh-CN / Admin en，但必须避免把 Business Content 错误放进 UI Translation；系统 UI 与企业知识内容继续分离。

## 十九、P2 RBAC

炎酷 CMS 已有 Admin / Editor 基础角色。GEO Website OS 已有权限基础，下一步建议：Owner / Admin / Editor / SEO Manager / Content Manager，但现在不做复杂企业级 IAM。v1.1 只解决：谁能看 / 谁能改 / 谁能发布 / 谁能管理系统。

## 二十、P2 AI Image

炎酷 CMS 已把 AI 生图、归档、AI 标识、素材管理串起来。GEO Website OS 可借鉴闭环：Prompt → Generate → Media → AI Metadata → Usage，但不在 v1.1 做成独立"AI 图片产品"，优先级低于 AI Content / Media Library / Lifecycle / Inquiry / Analytics。

## 二十一、P2 FAQ / Help Center

传统 CMS 很容易做、但 GEO Website OS 可以做得更好。不做 FAQ Table，而是 Content(type=faq) + Question/Answer semantic structure + Entity relation，最终 FAQ → Entity → Schema → GEO → Search，直接进入 Entity Graph。

## 二十二、P3 传统 CMS 能力不追求 1:1

- **友情链接**：不优先；未来可考虑 ExternalReference，而不是传统 Link Table。
- **无限级栏目树**：不复制；Category + Entity Graph + Content + Composition 已能表达更丰富的知识关系。
- **传统 UEditor**：不把传统富文本编辑器作为核心内容模型，继续以 Blocks / Sections / Structured Content / Semantic Data 为基础。

## 二十三、Backup / Upgrade

当前已有基础，v1.1 重点不是重新开发，而是把 Release Evidence 补完整。TD-168 明确 geo:upgrade / geo:backup / geo:rollback 还缺完整自动化测试。v1.1 目标：Backup E2E / Upgrade E2E / Rollback E2E / Migration failure / Data integrity / Artifact integrity，从"有升级系统"变成"升级系统已经证明可靠"。

## 二十四、v1.1 四条产品主线

不把 20 个功能散着做，重组为四条线：

- **A. Content Operations**：Lifecycle / Scheduled Publish / Trash / Page Manager / Media Library / Translation Workflow
- **B. Conversion Operations**：Inquiry Center / Attribution / Landing Pages / CTA analytics / Spam
- **C. GEO Operations**：Health / Coverage / Content Health / Entity Health / GEO Graph / AI Content / AI Batch
- **D. Platform Operations**：Template / Storage / Analytics / Backup / Upgrade / RBAC

## 二十六、最重要的产品判断

不要形成"炎酷 CMS 有 23 个功能 → 我们也必须有 23 个功能"，而应形成：

```
成熟 CMS → 成熟运营能力 → 抽象能力本质 → 映射到 GEO Native 架构
```

最终：Traditional CMS（Content-centric）→ GAP → GEO Website OS（Entity-centric）：Content → Composition → SEO → GEO → Health → Coverage → Conversion → AI Production。

## 二十七、v1.1 成熟度目标

不再用"功能数量"作为完成标准，而用闭环：

```
建站 → 初始化 → 创建 Entity → 创建 Content → 组织 Page → 发布
→ SEO / GEO 自动生成 → Health → Coverage → 访问 → 询盘 → Attribution
→ 分析 → 更新 → 定时发布 / 下线 → 归档 / 恢复 → AI 辅助生产
→ 再次 Health / Coverage → 持续运营
```

当这条链闭合，GEO Website OS 才真正从"GEO 官网系统"变成"企业 GEO Website Operating System"。

## 二十八、最终 Gap 结论

- **应该补**：Lifecycle / Scheduled Publish / Trash / Page Manager / Media Library / Inquiry Center / Attribution / Analytics / Translation Workflow / Object Storage / AI Content / AI Batch / Release Evidence
- **应该增强**：Template / Composer Preview / RBAC / Admin i18n
- **应该保持现有 GEO Native 架构，不重新设计**：Entity / EntityRelation / Registry / PublicIndex / PublicUrl / SeoMeta / Schema / GEO Graph / Health / Coverage
- **不建议照搬**：传统栏目树 / 传统友情链接 / 传统富文本中心 / 传统"AI 写文章"模型 / 传统 SEO Score / 传统 CMS 第二套数据模型

## 二十九、v1.1 产品定义

> **GEO Website OS v1.1 — Enterprise Content & GEO Operations**

不是"补齐 CMS 功能版"。v1.0 解决能不能成为一个真正的 GEO Website；v1.1 解决企业能不能长期、高效、规模化运营这个 GEO Website。

## 三十、与当前 v1.0 的关系

当前 v1.0 Architecture Frozen、19A Release Readiness PASS、P0=0、P1=0。这些 v1.1 Gap **不是 v1.0 缺陷、不是当前 Release Blocker**，进入 v1.1 Product Maturity Roadmap，并继续尊重 Architecture Freeze：

```
新增能力 → 独立 Discovery → 架构影响评估 → 必要时 Architecture Change Review
        → Implementation → Gate
```

不得因为成熟 CMS 存在某个功能，就直接解除 v1.0 Architecture Freeze。
