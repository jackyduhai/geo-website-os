# GEO Web OS 工程验收原则

- **状态**：ACCEPTED（2026-10-08，RC-11 收口时确立）
- **适用范围**：所有后续版本的开发、验收与发布决策
- **来源**：RC-11（504f71d → f4d06a1）期间四个真实缺陷，每条都经过人工验收或变异测试验证
- **性质**：不是理论教条，是**被现实验证过的失败清单**

---

## 一、四条不等式（核心）

```text
HTTP 200          ≠ 产品可用
字节不同          ≠ 模板真的不同
Token 改变        ≠ 用户视觉真的改变
测试通过          ≠ 测试走对了路径
```

这四条把验收从「技术正确性」推进到「**结果真实性**」。

### 每条的真实来源

| 不等式 | 真实缺陷 | 当时的错误信号 | 真相 |
|---|---|---|---|
| `200 ≠ 可用` | Logo 路径缺 `/storage` | HTTP 200、HTML 正常 | 图片 404，浏览器显示 alt 文本，视觉上「公司名重复两次」 |
| `字节不同 ≠ 模板不同` | `ensure()`漏调 `RecipeApplier` | 两预览站 HTML 差 13 字节，看起来「有差异」 | 区块全是骨架 Seeder 的，两个模板长得一样 |
| `Token 改变 ≠ 视觉改变` | 站点设置永久盖住主题种子 | `--brand` 变量值有变化 | 前台永远显示那一个颜色，切换主题形同虚设 |
| `测试通过 ≠ 走对路径` | 同上 | 8 个测试全绿 | 测试验证的是控制流安全，从没验证「模板 A → A 的内容」 |

第四条最危险：它会让**测试数量成为虚假的安全感**。

## 二、由此推出的硬性要求

### 2.1 每条断言必须回答「它在验证什么语义」

写测试前先回答：如果这个断言错了，说明产品哪里不对？
答不出来，说明它只是控制流断言，不产生真实保护。

```php
// ✗ 控制流断言：跑了就知道
$this->assertTrue($preview !== null);

// ✓ 结果语义断言：错了就知道哪块结构没落地
$this->assertSame($declared, $landed, 'recipe 声明与落地不一致');
```

### 2.2 新增测试必须做变异验证

**测试全绿不等于测试有效。** 唯一证明方式是故意改坏代码，看测试是否失败。

```text
变异：删掉 RecipeApplier::apply() 循环
  改动前 12 tests → 全绿（假绿）
  改动后新测试   → 失败，信息直指根因（有牙齿）
```

变异类型至少覆盖：漏调用 / 顺序错乱 / 条件短路 / 源数据被改。

### 2.3 视觉验收必须落到「元素实际计算样式」

CSS 变量值变化不算证据。要读回**渲染后元素**的 `getComputedStyle`，
并用真实鼠标事件触发交互态。

```javascript
// ✗ 读变量
getPropertyValue('--brand')

// ✓ 读元素 + 真实 hover
el.hover(); await wait(600);
getComputedStyle(el).backgroundColor
```

### 2.4 「看起来空」必须用语义计数交叉验证

截图里的空白不等于缺陷。必须用 chars / cards / links / 文本命中数交叉判断。

```text
本轮实证：预览站卡片区看似空白
  → 逐区块实测：product_grid chars=156 cards=4 links=4
  → 真相：图片占位（entities.metadata.image 为 null），真实站同样无图
  → 结论：既有设计，不是缺陷
```

**没有语义计数就下「渲染缺陷」结论，等于用直觉下结论。**

### 2.5 测试环境的「不可靠」结论必须有探针数据

以「RefreshDatabase 下不可靠」为由放弃测试前，先写探针实测。
本轮实测推翻了这条既有结论——同一路径完全可用。

### 2.6 验收脚本自身可能骗人

```text
本轮实证：主题切换「无效」
  → 真因：表单带 onsubmit="return confirm(...)"
  → 脚本未注册 dialog 处理器 → 提交被浏览器静默取消
  → 现象：URL 不变、DB 无变化、token 不变
  → 差点误判为「H1 修复无效」并去「修」一个没坏的代码路径
```

**先确认测试自己跑通了，再相信它的结论。** 这与 RC-9 误判 P0 是同一类错误。

## 三、分层验收标准

```text
自动化         状态 / 数据 / 隔离 / 回收 / 安全边界 / 声明→落地契约
   +变异       故意改坏，验证测试会失败
HTTP 验收      status / headers / 可见文本量 / block 数量 / 数据来源
浏览器验收     实际计算样式 / 真实 hover / 暗色模式 / 首屏结构 / 图片 / CTA
真实产品路径   管理员真实点击的完整链路
```

**下层通过不代表上层通过。** 每层都要独立取证。

## 四、对 AI 输出的特别要求

GEO Web OS 的产物是给 AI 读的，真实性要求更高。

```text
llms.txt / geo.json / JSON-LD / sitemap
  → 「有输出」≠「输出正确」
  → 必须验证：值来自哪个 SoT、多语言是否泄漏、跨站是否泄漏
  → D-02 就是这么抓出来的：两个出口数据源不同源，AI 得到矛盾答案
```

同理适用于 Content Engine：AI 产出的草稿必须过
`Evidence → Coverage → Health → Human Review` 才能发布，
不允许「AI 写了」直接等于「内容可信」。

## 五、提交前的自查清单

```text
□ 这个断言验证的是「结果语义」还是只是「控制流」？
□ 新测试做过变异验证吗？改坏代码它会失败吗？
□ 涉及视觉的，读的是元素计算样式还是仅 CSS 变量？
□ 判定「为空 / 缺失」时，有没有用语义计数交叉验证？
□ 有没有以「环境限制」放弃过测试？有探针数据支撑吗？
□ 验收脚本自身可靠吗（对话框 / 等待条件 / 代理 / 端口）？
□ 提交里是否混入本机路径、临时数据、测试凭据？
□ 版本边界是否保持干净（不动已发布 tag）？
```

---

## 六、一句话总结

> **不要只证明系统「运行了」，要证明系统「产生了正确结果」；
> 不要只验证测试「通过了」，要验证测试「真的验证了目标」。**

这套标准后续继续用在 GEO、AI 输出、模板、SEO、性能与安全上，
比继续增加测试数量更有价值。
