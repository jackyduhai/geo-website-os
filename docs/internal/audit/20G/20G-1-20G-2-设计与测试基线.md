### 2.2 C-5 三态语义实测

`mapPayload` 尾行（`GeoflowSync.php:257`）：
```php
return array_filter($attrs, fn ($v) => $v !== null, ARRAY_FILTER_USE_BOTH)
    + ($existing ? $existing->only(['slug', 'category_id', 'group_id']) : []);
```

| Payload | `summary` 结果 | `geo_boundary` 结果 |
| --- | --- | --- |
| 字段缺失（不修改） | 被丢弃 ✅ | 被丢弃 ✅ |
| **显式 `null`（应清空）** | **被丢弃 ❌** | **被丢弃 ❌** |
| 显式 `""` | 写入 `''` ✅ | 被丢弃（`empty()` 判定） |

**判定：C-5 成立**。上游无法清空字段。GEO 语义后果：清空 `geo_boundary` 是「该内容不再适用」的标准信号，当前无法表达 → GEO 事实错误。

**规格：三态语义 + 非法值必须 422，必须写入契约**

| Payload 形态 | 语义 | 实现要求 |
| --- | --- | --- |
| 字段不存在（missing） | 不修改 | 用 `array_key_exists` 判断，不用 `array_filter` |
| `"field": null` | **清空** | 显式写 `null` 到模型 |
| `"field": "valid"` | 正常写入 | 规范化后写入 |
| **`"field": "invalid"`** | **拒绝** | **422 + 明确 code，不写库** |

> **口径修正（评审第 2 条）**：原规格写「`category_slug` 解析失败写 null」是**危险的**。
> `category_slug = "不存在的分类"`（上游数据错误）与 `category_slug = null`（上游明确要求清空）
> 是两种完全不同的业务语义。若把解析失败当 null 处理，等于**把上游输入错误转换成合法的
> 数据清空动作** —— 上游拼错一个 slug，官网就把该内容的栏目归属清空了，且返回 200。
>
> 正确区分：
> ```
> missing        → 不修改
> null           → 清空
> valid value    → 正常写入
> invalid value  → 422（code: validation），SyncLog 记 reject
> ```
>
> 适用范围：`category_slug`、`group_slug`（引用型字段，解析失败必须 422）、
> `type`（枚举）、`published_at`/`reviewed_at`/`review_due`（日期格式）、
> `geo_evidence`/`geo_faq`/`geo_key_facts`（JSON 合法性，见 C-12）。


### 2.3 C-4 指纹覆盖实测

**20F.1 已修复部分**：`upsert:97-101` 已用 `clone $existing` + `fill($attributes)` 计算**合并投影后的指纹**，并有注释说明「以合并现有内容后的最终状态计算指纹，部分推送不会误判为变化」。这部分是正确的。

**剩余缺口**：`computeHash`（`Content.php`）仍只覆盖 7 字段。逐字段实测：

| 变更字段 | hash 是否改变 | 应纳入 |
| --- | --- | --- |
| `slug` | ❌ 不变 | ✅ 是（换 URL 是 GEO 关键变更） |
| `type` | ❌ 不变 | ✅ 是 |
| `category_id` | ❌ 不变 | ✅ 是 |
| `group_id` | ❌ 不变 | ✅ 是 |
| `owner` | ❌ 不变 | ✅ 是 |
| `geo_faq` | ❌ 不变 | ✅ 是（FAQ 是 GEO 核心输出） |
| `geo_key_facts` | ❌ 不变 | ✅ 是 |
| `source_note` | ❌ 不变 | ✅ 是（来源影响可信度） |
| `reviewed_at` | ❌ 不变 | ✅ 是（核定时间影响事实时效） |
| `review_due` | ❌ 不变 | ✅ 是 |

**判定：C-4 成立 —— 10 个受管字段未进指纹。**

失败场景：上游改 slug → 指纹相同 → 返回 `action=skip` + HTTP 200「内容未变化」→ **上游永不重试，URL 永久错误**。这是最难排查的一类静默数据错误。

**规格：Canonical Sync Projection**

**关键：不能简单地把 `FILLABLE` 全部丢进 hash。** `FILLABLE` 回答的是「允许写哪些列」，
hash 需要回答的是「哪些字段构成**这条内容的对外事实**」。两者不一定等价 —— 例如
`external_source`、`synced_at` 是系统生成字段，参与 hash 会导致每次同步都判定为变化。

必须建立**单一契约常量**作为唯一事实源：

```php
/**
 * GEOFlow 同步受管字段契约（20G-2）
 *
 * 这是「外部同步事实」的唯一事实源，由它派生：
 *   - Validation（哪些字段需要类型/长度/格式校验）
 *   - Normalization（哪些字段需要规范化）
 *   - Hash Projection（哪些字段参与内容指纹）
 *   - Revision Snapshot（哪些字段写入历史快照）
 *   - Nullable 语义（哪些字段允许显式 null 清空）
 *
 * 不属于同步事实的字段（系统生成 / 人工锁定标记）不得参与 hash，
 * 否则每次同步都会误判为「内容已变化」，形成同步风暴。
 */
public const SYNC_MANAGED_FIELDS = [
    // 内容事实
    'type', 'title', 'slug', 'summary', 'body',
    // 结构归属
    'category_id', 'group_id',
    // GEO 事实（四要素 + FAQ + 关键事实）
    'geo_conclusion', 'geo_explanation', 'geo_evidence', 'geo_boundary',
    'geo_faq', 'geo_key_facts',
    // 责任与来源
    'owner', 'source_note',
    // 时效
    'published_at', 'reviewed_at', 'review_due',
];

/** 明确排除在 hash 之外的系统生成字段（附理由，防误加） */
public const SYNC_GENERATED_FIELDS = [
    'external_id'      => '业务主键，本身即幂等键',
    'external_source'  => '系统生成（恒为 geoflow）',
    'synced_at'        => '每次同步都变，纳入则永不 skip',
    'content_hash'     => '哈希结果本身',
    'status'           => '由 auto_publish + 门禁推导，非外部事实',
    'lock_manual'      => '人工锁定标记，由人工控制',
    'slot'             => '叙事插槽，不走 GEOFlow',
    'cover_id', 'og_image_id' => '媒体关联，单独演进',
];
```

派生关系：

```
SYNC_MANAGED_FIELDS
        ↓
   ┌────┴────┬──────────┬──────────┐
Validation  Normalize  Hash      Revision
（类型/长度/  （slug/日期/ （Canonical （快照）
  格式/枚举）  JSON解析）  Projection）
```

**实施要求**：
1. `computeHash()` 不再手工列举字段，改为遍历 `SYNC_MANAGED_FIELDS`
2. `mapPayload()` 的白名单改为 `SYNC_MANAGED_FIELDS`（去掉 `published_at` 需单独处理的情况见下）
3. `ContentRevision::snapshot` 用同一常量
4. 新增测试断言：**修改任一 `SYNC_MANAGED_FIELDS` 字段 → hash 必须变化**（数据驱动，不硬编码字段名）

> `published_at` 特殊说明：它在 `SYNC_MANAGED_FIELDS` 内参与 hash（发布时间是 GEO 事实），
> 但写入时若为空且 `auto_publish=1`，Service 会填 `now()`。这个「系统补的发布时间」
> 必须在 hash 计算**之后**才填，否则每次同步 hash 都变。

### 2.3.1 `hash_schema_version` 的使用规则（已按评审补充）

```php
/** 哈希投影契约版本。改动 SYNC_MANAGED_FIELDS 的组成/语义时必须 bump。 */
public const HASH_SCHEMA_VERSION = 2;
```

**必须遵守的规则（评审第 3 条）**：

| 要求 | 说明 |
| --- | --- |
| **版本变化不得触发全量无条件重算** | bump 后不主动批量重算存量 `content_hash` |
| **版本作为 hash 输入的一部分** | `hash('sha256', json_encode(['v' => VER, 'f' => $projection]))` |
| **存量数据保持 skip 语义** | 旧 `content_hash` 不含 `v`，与新 hash 必然不等 → 首次推送会判定为「变化」并重算，**这是预期行为，且仅限被推送的内容** |
| **禁止在部署时全表重算** | 绝不能写 `Content::all()->update(['content_hash' => ...])` 之类的迁移 |

**为什么这条规则重要**：若部署时无条件重算全站 hash，或者 bump 版本后让「版本差异」等价于
「内容变化」，那么一次版本升级会瞬间把整个站点的内容全部判定为已变化 —— 对上游而言
就是一次**同步风暴**（几千条内容全部重推），对 GEO 事实而言是一次虚假的大规模更新。
正确语义是：**版本只影响「本次计算出的 hash 与存量 hash 的可比性」，存量 hash 保持原值，
直到该条内容被真正推送时才用新算法重算。**

> 注：当前数据规模小（开发库 contents=3），同步风暴不会造成实质影响。但这是**契约设计**问题，
> 必须现在定死，否则 v1.1 内容量上来后无法回溯修改。

```php

//         ├──> validateAndNormalizePayload(): array
// check  ─┘
//
// 职责：
//  1. 类型断言：所有入模型字段必须 is_scalar 或 null（数组/对象 → 422）
//  2. 长度上限：与 ContentController::validateForm() 同源
```

### 2.6 20G-2 建议实施顺序（已按评审调整：Contract Schema 先行）

```
Step 1  定义 SYNC_MANAGED_FIELDS / SYNC_GENERATED_FIELDS / HASH_SCHEMA_VERSION 契约
        （唯一事实源，后续所有步骤派生自它）
            ↓
Step 2  validateAndNormalizePayload()（upsert / check 共用）
        类型断言 + 长度上限 + 枚举 + 日期格式 + JSON 合法性 + 引用解析
        非法值一律 422，不做「猜测性降级」
            ↓
Step 3  mapPayload 三态 Field Semantics
        missing / null / valid / invalid 四态显式区分
            ↓
Step 4  computeHash → Canonical Sync Projection
        遍历 SYNC_MANAGED_FIELDS + 版本号，禁止手工列举
            ↓
Step 5  State / Lock / Enable 边界
        assertEnabled() 覆盖所有写入口
        unpublish 补 lock_manual 判定 + ContentRevision 快照
            ↓
Step 6  Response Contract 统一
        { ok, code, message, external_id, request_id, data }
        成功补 changed_fields；错误补机器可读 code
            ↓
Step 7  DB 唯一约束 + 竞态兜底
        UNIQUE(site_id, external_id) 迁移
        捕获唯一键冲突 → 转为幂等/conflict 结果，不得 500
            ↓
Step 8  Contract Tests（8 个测试组，见 2.8）
```

**为什么把 Contract Schema 提到 Step 1**（评审第 3 条的同源风险）：
若先改 `mapPayload`、再改 `hash`、再改 `check`，每一层会各自理解一遍字段语义，
必然重新产生 Contract Drift —— 这正是 20G-2 要消灭的东西。契约常量先行，
后续步骤只是**消费**它，不各自定义。

### 2.7 并发竞态不得变成 HTTP 500（已按评审补充）

**评审第 4 条要点**：仅加 DB 唯一约束不够。

```
Request A                     Request B
   ↓                             ↓
检查 external_id 不存在 ✅        检查 external_id 不存在 ✅
   ↓                             ↓
INSERT（成功）                   INSERT（唯一键冲突）
   ↓                             ↓
返回 201                    ❌ 若不捕获 → QueryException → 500
```

DB 唯一约束只能保证「第二个最终失败」，**业务层必须把该失败翻译成契约内的结果**。

实施要求：

```php
// 新增 external_id 唯一约束后，upsert 的创建分支必须包在 try/catch 里
try {
    $content = new Content($attributes);
    $content->external_id = $externalId;
    $content->content_hash = $content->computeHash();
    $content->save();
    $action = 'create';
} catch (\Illuminate\Database\QueryException $e) {
    // 唯一键冲突 = 并发重复推送 = 幂等命中，不是服务端错误
    if ($this->isUniqueViolation($e)) {
        $existing = Content::where('external_id', $externalId)->lockForUpdate()->first();
        SyncLog::write('in', 'conflict', [
            'external_id' => $externalId,
            'content_id'  => $existing?->id,
            'status'      => 'warn',
            'message'     => '并发重复推送，命中唯一约束，已转为幂等结果',
            'payload'     => $payload,
        ]);

        return [
            'ok' => true, 'action' => 'skip', 'status' => 200,
            'content' => $existing,
            'message' => '并发重复推送，内容已存在',
        ];
    }
    throw $e;   // 非唯一键异常仍按 500 上抛
}
```

**必须新增测试**（`GeoflowConcurrencyTest`）：

| 用例 | 期望 |
| --- | --- |
| 同 `external_id` 顺序推 2 次 | 2 条记录？否，1 条；第 2 次 `action=skip` |
| 同 `external_id` 并发推 2 次 | 1 条记录；**无 500**；两次响应均符合契约 |
| 并发后 `status` 查询 | 返回同一条内容 |
| 迁移后存量重复数据 | 迁移前必须先清理，否则唯一索引创建失败 |

> 迁移安全：`UNIQUE(site_id, external_id)` 上线前需先探测存量重复
> （`SELECT site_id, external_id, COUNT(*) FROM contents WHERE external_id IS NOT NULL GROUP BY 1,2 HAVING COUNT(*)>1`），
> 有重复则迁移中止并报错，不可静默删数据。

### 2.9 Response Contract 统一格式（已按评审补充 `request_id`）

**成功**：
```json
{
  "ok": true,
  "action": "created|updated|skipped",
  "external_id": "gf-001",
  "request_id": "01J8X...",
  "changed_fields": ["title", "slug"],
  "data": { "id": 12, "status": "published", "url": "https://…", "content_hash": "…" }
}
```

**失败**：
```json
{
  "ok": false,
  "code": "validation|disabled|conflict|not_found|gate_rejected|server_error",
  "message": "人可读说明",
  "external_id": "gf-001",
  "request_id": "01J8X...",
  "errors": ["字段级错误"]
}
```

`request_id` 作为**工程增强项**（不单独升问题编号），价值：
GEOFlow 是外部系统调用，线上排障需要 `上游日志 ↔ SyncLog ↔ HTTP 响应` 三方对账，
没有 correlation id 会很痛苦。实现上可用 `Request::header('X-Request-Id')` 透传，
缺失则生成 ULID，并把同一个值写进 `SyncLog.payload`。

### 2.10 Revision 快照字段要求（已按评审补充）

`unpublish` 必须写 `ContentRevision`，且快照至少包含：

| 字段 | 说明 |
| --- | --- |
| `content_id` | 目标内容 |
| `before` | 变更前状态（至少含 `status`） |
| `after` | 变更后状态 |
| `actor` / `source` | `geoflow` |
| `reason` | `上游要求下架` |
| `timestamp` | 由 `created_at` 承担 |
| `external_id` | 便于按上游 ID 追溯 |

**理由**：`status` 虽非正文，但改变了前台事实状态（内容从可见变不可见），
属于「内容变更」，必须可回滚。`ContentRevision` 现有 schema 是 `snapshot` JSON，
可直接容纳 `before`/`after` 结构。
