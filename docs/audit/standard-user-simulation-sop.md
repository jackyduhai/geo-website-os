# 标准化模拟人测试流程 SOP（Standard User Simulation SOP）

- **文档版本**：v1.0
- **建立日期**：2026-09-29
- **适用仓库**：`D:\GEO-OS-rewrite\geo-website-os`（Laravel 12 + PHP 8.4 + SQLite，多站点 GEO 内容管理系统）
- **性质**：可复用的发布前人工/模拟人测试标准。每次发布候选版本（release candidate）必须按本 SOP 全量执行并留痕。
- **配套基线**：
  - 功能矩阵：`docs/audit/20A-feature-smoke-test-matrix.md`（190 项 FT）
  - 功能矩阵报告：`docs/audit/20A-feature-smoke-test-final.md`
  - 技术债务登记：`docs/audit/technical-debt-registry.md`

## 0. 为什么需要本 SOP（历史教训）

此前的"功能冒烟测试（FBS）"声称 190/190 PASS，但用户"登录进来点几次"就暴露了 LOGO 被压变形、语言切换失效、导航横向溢出等基础问题。根因是测试停留在三个浅层：

1. **HTTP 200 = 通过**：页面能打开就算过，不核对实际渲染。
2. **链接存在 = 可用**：只断言链接/按钮在 HTML 里，不真实点击、不验证往返后的最终状态。
3. **单点验证 = 整体通过**：一个点过了就假设同类都过，不做横向扩散。

本 SOP 用七条强制规则补盲，任何一条未执行都不得宣称"模拟测试通过"：

| 编号 | 盲区 | 强制规则 |
|---|---|---|
| G1 | 视觉变形 | 图片/LOGO 必须核对**渲染宽高比 vs 自然宽高比**（横版被 CSS 压成正方形时 HTTP 仍 200） |
| G2 | 真实交互往返 | 每个切换/状态动作必须**真实点击并验证最终状态**（URL + 内容 + 派生输出）；语言切换必须完整往返 zh→en→zh |
| G3 | 四面验证 | UI 结果 = HTTP 结果 = DB 结果 = 派生输出（sitemap/geo.json/schema/search/llms） |
| G4 | 多视口溢出 | 关键页面在 375/390/768/1280/1440 实测 `scrollWidth - clientWidth = 0`，导航所有按钮可点击 |
| G5 | 异常输入矩阵 | 空 / 重复 slug / 超长 / XSS / 特殊字符 / 重复提交 / 后退刷新 |
| G6 | 问题扩散 | 单点问题必须横向检查同类（一个语言页异常→查全部 zh/en；一个删除异常→查全部实体） |
| G7 | 测试纪律 | **禁止"为了让测试变绿"改业务规则**；测试中发现问题先记录，不一边测一边改 |

## 1. 角色、状态与判定口径

### 1.1 角色

- **测试执行员（Tester）**：按 SOP 执行、记录、留证据，不修改业务代码。
- **诊断员（Diagnoser）**：对 FAIL 项做根因定位（触发→机制→症状）。
- **修复员（Fixer）**：仅在授权后对 Critical/Major 做原因级修复。
- **发布裁定人（Release Owner）**：人工，依据报告决定是否放行。

### 1.2 用例状态（每项唯一）

| 状态 | 含义 |
|---|---|
| PASS | 所有断言（含四面）通过，证据齐全 |
| FAIL | 断言失败，已记录现象与证据 |
| BLOCKED | 因前置缺陷/环境无法执行（必须注明阻塞来源用例号） |
| NOT-COVERED | 计划内但本轮未执行（必须注明原因，不得静默跳过） |
| N/A | 经确认不适用（须回链确认依据） |

### 1.3 问题分级

| 级别 | 定义 | 处理 |
|---|---|---|
| **Critical（P0）** | 安全漏洞、数据损坏/丢失、整站不可用、发布链路阻断 | 必须修复并回归后才可继续 |
| **Major（P1）** | 核心功能不可用或结果错误（登录、发布、CRUD、多语言、多站隔离、关键页面） | 必须修复并回归 |
| **P2** | 重要功能受阻但有绕过路径；明显样式/交互缺陷 | 本轮可登记 TD，发布裁定人决定 |
| **P3** | 打磨类：文案、对齐、轻微视觉瑕疵、边角交互 | 登记 TD |

> 分级判断只看"对用户目标的影响"，不看修复难度。难以判定时上调一级。

## 2. 阶段 A — 环境冻结与基线确认

执行任何测试前，先冻结并记录"测试指纹（fingerprint）"，报告中必须逐项可回查：

```
revision（git HEAD，须 git status 确认 clean）
依赖与运行时（PHP 版本 C:\php84\php.exe -v；composer.lock 摘要）
入口（http://127.0.0.1:8000；后台 /admin/login）
凭据（admin@example.com / Admin@123456）
数据基线（contents/entities/pages/media/relations/inquiries/users 计数）
缓存状态（view:clear、page-cache:clear 后开始）
测试人 / 日期 / 浏览器版本 / 视口集合
```

操作清单（PowerShell）：

1. `git log --oneline -1` 与 `git status --short`（必须 clean）。
2. `Get-Process php` 确认无残留卡死进程；预览服务 `php artisan serve` 已在 8000 端口运行（**不要重复起服务**）。
3. `C:\php84\php.exe artisan view:clear`；`C:\php84\php.exe artisan page-cache:clear`。
4. 记录 DB 基线计数（通过 PHP 脚本或 `php artisan tinker` 只读查询）。
5. 冒烟连通：`GET /admin/login` 返回 200。

> 若工作树不 clean、HEAD 不符、或基线数据与预期不符，**停止**并先确认来源，禁止在不可信起点上测试。

## 3. 阶段 B — 功能清单建立（Inventory）

目标：建立"被测对象全集"，确保没有按钮/功能/页面被遗漏。清单四来源合并去重：

### 3.1 路由清单

- `C:\php84\php.exe artisan route:list --columns=method,uri,name,action` 导出全量路由。
- 按中间件/前缀分组：Admin（约 142）、Frontend（约 47）、API（约 5）。
- 每条路由标注：页面型（返回视图）/ 动作型（写操作后 302）/ JSON 型（接口）。
- 标记需要重点验证的写操作：POST/PUT/PATCH/DELETE。

### 3.2 导航清单

- 后台：逐项列出侧边栏/顶栏导航项（约 30 项，含分组链接），记录其目标 URL 与可见层级。
- 前台：页眉导航、页脚链接、语言切换器、面包屑、CTA 按钮、分页。

### 3.3 交互控件清单（逐页枚举）

在每个页面上枚举并登记：表单（输入框/下拉/单选/复选/文件上传/富文本/Markdown）、按钮（提交/保存/删除/发布/下线/批量操作）、切换器（语言/站点/Tab/开关）、链接卡片、搜索框、排序/筛选/分页、模态框、下拉菜单、复制/下载按钮。

### 3.4 页面类型与实体清单

- 前台页面类型（约 18 类）：首页、列表、文章、产品、实体详情、关系、联系、关于、搜索、404 等。
- 实体类型（8 种）与设置组（8 组）逐一登记。

### 3.5 覆盖率口径

- **路由覆盖率** = 已执行路由数 / 清单路由数。
- **控件覆盖率** = 已真实操作控件数 / 清单控件数（"看到了"不算，"操作了并验证了"才算）。
- **页面类型覆盖率** = 已测页面类型数 / 18。
- 三个口径必须分别报告，不得用一个高覆盖率掩盖另一个。

## 4. 阶段 C — 测试矩阵编号

每个测试项给唯一编号，写入矩阵表（沿用并扩展 FBS 的 FT 编号体系，新增模拟项用 `SIM-xxx`）：

| 字段 | 说明 |
|---|---|
| ID | SIM-001 起，连续编号 |
| 模块 | Dashboard / Content / Entity / Site / Settings / Frontend… |
| 功能 | 一句话描述 |
| 入口 | 字面 URL + 控件定位（如"侧边栏 > 内容 > 新建"） |
| 操作 | 真实操作步骤（点击/输入/选择/提交） |
| 四面断言 | UI / HTTP / DB / 派生输出 各自预期 |
| 视口/语言 | 适用的视口与语言 |
| 状态 | PASS/FAIL/BLOCKED/NOT-COVERED/N/A |
| 证据 | 截图路径、请求/响应摘要、DB 行值、派生输出片段 |
| 问题号 | FAIL 时关联 BUG-xxx |

矩阵即测试合同：**预期在执行前写好**，禁止执行后用"实际结果"反改预期（G7）。

## 5. 阶段 D — 四面真实验证（核心，G3）

对每个功能、尤其每个写操作，必须在**四个面**对拍，任何一面不一致即 FAIL：

### 面 1：UI（浏览器真实结果）

- 真实点击/输入/提交（浏览器自动化见 §9），观察页面可见结果、提示文案（成功/失败 toast、内联错误）、跳转后页面。
- 不能只看"有没有这个按钮"，要看"点了之后发生了什么"。

### 面 2：HTTP（请求/响应）

- 记录请求方法、URL、状态码（302 的 Location）、响应体关键片段。
- 动作型接口预期 302 到正确目标；校验失败预期 422/回表单带错误；异常预期 500 即 FAIL（除非是预期内的受控错误页）。

### 面 3：DB（持久化状态）

- 操作后直接读库核对：字段值、外键、状态枚举、软删标记（deleted_at）、关系表行、站点归属（site_id）。
- 删除/级联要核对相关行是否按预期清理或保留。

### 面 4：派生输出（前台与衍生制品）

- 写操作后，前台对应页面、列表、搜索、`sitemap.xml`、`robots.txt`、`geo.json`、`llms.txt`、页面内 JSON-LD/schema 等是否同步反映。
- 例如：发布一篇文章 → 前台列表出现、详情可访问、sitemap 含该 URL、JSON-LD 字段正确；下线 → 前台 404、sitemap 移除、缓存不残留旧 200。

> 四面必须"同一次操作"连续对拍。只做 UI 或只做 HTTP 都不算完成。

## 6. 阶段 E — 视觉渲染验证（G1）

专抓"HTTP 200 但画面错误"。对每个含图页面（LOGO、OG 图、产品图、实体图、内容配图、占位图、favicon）执行：

1. 读取自然尺寸：`naturalWidth` / `naturalHeight`，计算自然宽高比 `r_nat`。
2. 读取渲染盒：`getBoundingClientRect()` 的 width/height，计算渲染比 `r_render`。
3. 断言：`abs(r_render - r_nat) / r_nat ≤ 0.02`（2% 容差），否则记 **变形 FAIL**。
4. 检查图片是否在容器内 `object-fit` 正确、无拉伸/裁切丢主体/留白异常；图片未加载（broken image / naturalWidth=0）单列 FAIL。
5. 检查横版 LOGO 是否被压成正方形、SVG  viewBox 是否被非等比缩放。
6. 背景图/封面在不同视口下的主体可见性。

> 同一 LOGO/图片在页眉、页脚、登录页、后台、邮件模板中可能用不同容器，必须逐一核对（G6）。

## 7. 阶段 F — 真实交互往返与状态切换（G2）

### 7.1 通用往返断言

每个动作验证"最终状态"三件套：**最终 URL 正确 + 页面内容正确 + 派生输出正确**。

- 开关/Tab/折叠菜单：展开→内容出现；收起→消失；重复点击行为确定。
- 下拉/模态：打开、选择、关闭、取消、点击遮罩/Esc 各路径都要测。
- 表单：填写→提交→成功反馈；校验失败→停留并标错；取消→放弃变更。

### 7.2 语言切换（强制完整往返）

1. 从中文页点语言切换到 EN：断言目标 URL 是正确的英文路由（不是停在原 URL、不是 404）。
2. 断言英文页**纯英文**：正文、导航、按钮、面包屑、SEO title/description、JSON-LD 均为英文，**无中英混合、无未翻译键原样露出**。
3. 再切回中文：断言回到正确中文 URL，内容纯中文。
4. 切换后刷新页面、新开标签直入该 URL，语言保持正确。
5. 一个语言页出问题 → 横向检查**全部 zh/en 页面**（G6）。

### 7.3 状态机与缓存

- 内容状态：draft → published → draft（下线）→ 删除，逐转移核对 DB 状态 + 前台可见性 + 缓存。
- 发布/下线/删除后强制检查：前台是否仍返回旧缓存（命中旧 200 属 FAIL）；必要时 `page-cache:clear` 前后对比，确认缓存失效逻辑真实生效。
- 站点切换：切换管理站点后，列表/统计/前台是否全部切换到新站点，无串站。

## 8. 阶段 G — 多视口 / 多语言 / 多浏览器（G4）

### 8.1 视口集合

固定测试：**375（小屏手机）、390（主流手机）、768（平板）、1280（笔记本）、1440（桌面）**。

### 8.2 横向溢出判定（每页每视口）

- 断言 `document.documentElement.scrollWidth - document.documentElement.clientWidth === 0`（为 0 才无横向溢出）。
- 同时检查 body 及关键容器无溢出；无元素被挤出视口、无文字被裁切。
- 导航在窄屏：汉堡菜单可打开、**所有导航项可点击可达**、切换后可收起；无按钮重叠/错位。
- 表格/代码块/长 URL/卡片网格在窄屏是否横向滚动或正确堆叠。

### 8.3 多语言

按 §7.2 对 zh/en 全量执行；日期、数字、货币等本地化呈现正确。

### 8.4 多浏览器

- 至少 Chrome（主测）；发布前建议补 Edge / Firefox 各跑核心路径（首页、详情、登录、CRUD、语言切换、联系表单）。
- 记录浏览器版本与差异。

### 8.5 必测"关键页面"集合

首页、全部主要列表/详情、联系/关于、搜索、404、后台 Dashboard、登录、主要 CRUD 列表与编辑页、设置页——每个都过 5 视口。

## 9. 阶段 H — 浏览器自动化操作约定

- 真实浏览器操作使用浏览器自动化（browser-use）：页面操作在 Chrome 中执行，先快照（snapshot）定位元素再动作，动作后重新快照验证；支持通过 CDP 直接设置视口、执行 JS（读取 naturalWidth、getBoundingClientRect、scrollWidth 等）。
- 桌面原生层面（窗口、多浏览器启动）用桌面控制；浏览器标签页内容用页面控制。
- **同一时间只允许一个执行者驱动浏览器**，避免多任务抢占同一 Chrome；HTTP/DB 类对拍可并行脚本化。
- 每次断言必须有证据：截图 + 关键 JS 读数 + 网络请求/响应。
- 动作失败先重新观察页面（元素可能已重排/刷新），不得凭旧坐标盲点。

## 10. 阶段 I — 边界与异常输入矩阵（G5）

对每个表单/写操作至少覆盖：

| 类别 | 输入/动作 |
|---|---|
| 空值 | 必填全空、仅空格、提交空表单 |
| 重复/冲突 | 重复 slug、重名、重复提交（双击/快速连点） |
| 长度 | 超长标题/slug（>255、>数据库列长）、单字符、emoji |
| 特殊字符 | 中文、中文 slug、空格、`/`、`?`、`#`、`&`、`%`、前后空格、全角字符 |
| 安全 | XSS 脚本片段、HTML/属性注入、SQL 片段、JSON 畸形（在 JSON 接口） |
| 类型 | 数字字段填字母、邮箱/URL 非法格式、文件上传错误类型/超大文件 |
| 会话 | 后退后重复提交、F5 刷新 POST、会话过期后提交、多标签页同时操作 |
| 数据极端 | Blank 空站点（0 数据）与 Demo 全量数据两端；分页到第 0 页/超界页 |

异常输入验证原则：

- 受控拒绝（422/错误提示、不入库、无副作用）= 正确。
- 500、报错堆栈外露、入库脏数据、XSS 被原样执行、重复产生多条 = FAIL。
- 安全类测试注意隔离：XSS 验证只在受控输入中观察转义，不污染真实数据；测试后清理。

## 11. 阶段 J — 权限与会话安全

- 未登录访问每个后台 URL → 重定向登录，无数据泄露。
- 登录后越权：访问/修改不属于当前站点的资源（IDOR）、用动词直接打写接口。
- 多站隔离：切换站点后不能读到/改到另一站点数据；前台不串站。
- 退出后后退不能进入后台、会话失效写操作被拒。
- CSRF：无 token / 跨站提交被拒。
- 权限相关任何疑似泄露按不低于 Major 记录。

## 12. 阶段 K — 问题扩散检查（G6）

发现任一 FAIL，必须横向排查同类，禁止"只修看到的那一个"：

| 单点发现 | 扩散排查范围 |
|---|---|
| 一个语言页异常 | 全部 zh/en 页面、导航/SEO/JSON-LD |
| 一个删除异常 | 全部 8 类实体、内容、关系、媒体 |
| 一个表单校验异常 | 全部表单（创建/编辑/设置/向导/联系） |
| 一个图片变形 | 全部图片位（LOGO/OG/产品/实体/配图/占位） |
| 一个视口溢出 | 全部关键页面 × 5 视口 |
| 一个缓存不失效 | 发布/下线/删除/切换/设置全部场景 |
| 一个接口 500 | 同类动作型接口全扫 |

扩散结果一并登记，区分"根因相同的一簇"与"相互独立的多个问题"。

## 13. 阶段 L — 回归与报告

### 13.1 修复授权与回归

- 测试中**只记录不修复**（G7）。测试结束、汇总分级后：
  - Critical/Major：经诊断员定位根因（触发→机制→症状），授权修复员做**原因级修复**；禁止用 sleep、盲目重试、放宽断言、吞错误代替原因级修复。
  - P2/P3：登记技术债务（`technical-debt-registry.md`），不扩大范围。
- 修复后：先跑定向（覆盖该问题及扩散面），再跑全量回归（约 20 分钟，串行，后台任务耐心等待，不反复打断）。
- 回归必须包含"受保护语义"核对：修复未改变无关功能、未改变正常/边界/异常路径。

### 13.2 污染扫描与复原

- 测试结束清理：临时脚本（保留下来的可复用工具除外）、临时 DB、临时文件、测试中创建的脏数据。
- 主库恢复到约定数据基线；`git status` 恢复 clean（报告与授权修复的提交除外）。
- 不残留卡死的 php 进程。

### 13.3 报告内容（放 `docs/audit/`）

1. 测试指纹与环境。
2. 覆盖率：路由/控件/页面类型三个口径。
3. 通过率：`PASS / (PASS+FAIL+BLOCKED)`，分母口径写明；**NOT-COVERED 单独列示，不得计入通过**。
4. 问题清单（分级、根因、扩散面、状态）。
5. 修复清单与回归结果（定向 + 全量，含测试框架输出的 passed/assertions/failed 数字）。
6. 派生输出与污染扫描结果、git 状态。
7. 明确的发布建议（放行 / 有条件放行 / 不放行），最终由发布裁定人人工裁决。

---

## 14. 通过率与"完成"的硬口径

- **不允许**用 HTTP 200、链接存在、页面能打开作为通过依据。
- 一个用例 PASS 的最低条件：真实操作 + 四面断言通过 + 视觉/视口（适用项）通过 + 证据齐全。
- 整体"模拟测试通过"的条件：
  1. 路由/控件/页面类型覆盖率达标（发布候选要求 100% 路由可达、关键页面 100% 过 5 视口）；
  2. Critical/Major = 0（全部已修复并回归）；
  3. P2/P3 有明确登记与裁定；
  4. 无 NOT-COVERED 未说明；
  5. 全量回归 0 failed、0 skipped；
  6. 工作树 clean、主库复原。
- 任一不满足，结论为"**不具备发布条件**"，不得用"基本可用""问题不大"等措辞升级语气。
